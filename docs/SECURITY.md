# Security and deployment notes

- URL parsing accepts exact Google Forms host/path combinations, disallows credentials, custom ports, fragments, prefill/edit tokens and unexpected queries, and normalizes URL parameters. Playwright intercepts all requests, blocks non-HTTPS/non-allowlisted destinations, validates IPv4 DNS results, disables service workers, and checks the resolved form URL. IPv6 destinations are deliberately rejected. Exact allowlisted Google names reduce user-controlled DNS/redirect risk; deploy browser workers behind an outbound network policy for defense in depth.
- The local fixture adapter requires `NODE_ENV=test` and exact `127.0.0.1` HTTP. It is called only by tests and never selected by REST, environment configuration or uploaded spreadsheets.
- XLSX uploads use memory buffers with byte/row limits, ZIP expansion preflight, template identity/fingerprint checks, exact headings/mapping, and formula/object rejection. Raw files are not saved. Do not raise limits without memory/load testing. Workbook contents are untrusted data.
- Passwords use bcrypt; sessions are HS256 signed with an external random secret and checked against a DB session version. Log out revokes all of that user's sessions. Production cookies require HTTPS and are HttpOnly and SameSite=Lax. Exact Origin checks protect mutations, including login. OAuth has a random short-lived state cookie; secrets and refresh tokens never reach the browser. The callback requires a live authenticated workspace session.
- API ownership filters cover forms, templates, uploads, batches, records and reports. Authenticated Socket.IO clients join only their own user room and their session is revalidated every minute. Published events contain no answers.
- Answers, uploaded validation payloads and refresh tokens use authenticated AES-256-GCM with random nonces. Hashes, form metadata and timestamps are not encrypted. Encrypt server disks, database backups and transport to managed databases. The built-in Compose network is intended for a single trusted host.
- Logs intentionally omit request bodies, cookies, query strings and answers. Browser errors are mapped to conservative messages to avoid leaking typed values. Authorization and report downloads are audited. An audit record is not a substitute for centralized tamper-resistant logs.
- The parser/worker limits and one-at-a-time defaults constrain resources but have not undergone a penetration test or production load test. Single-process rate limiting must become distributed before scaling API replicas.
- No CAPTCHA bypass, anti-bot evasion, proxy rotation, Google password collection or automatic reattempt after ambiguous submission exists. Authorization confirmation is mandatory for each batch, and an audit timestamp is stored.

## Dependency review

Development accepts `localhost` and `127.0.0.1` as aliases only on the configured frontend protocol/port. Production remains restricted to the single configured origin. REST CORS, mutation protection and Socket.IO share this allowlist; missing Origins and unrelated origins remain rejected for state-changing requests.

Same-origin Socket.IO polling GETs can omit Origin. For those handshakes only, `Sec-Fetch-Site: same-origin` is required when Origin is absent; an explicit unapproved Origin is always rejected. Session authentication is still mandatory before joining any private user room. REST mutation checks are unchanged.

The checked-in lockfile pins the tested installation. The initial dependency scan reported high/critical findings. Upgrading Zod and Vitest and overriding patched Prisma CLI dependencies removed those categories in the subsequent install audit. Moderate transitive findings remained, notably older glob/minimatch and UUID dependencies in ExcelJS/tooling. Some suggested npm fixes are breaking downgrades and were deliberately not applied blindly. ExcelJS's globbing/file-archive discovery and UUID buffer APIs are not exposed to user input by this application, but that is an exposure assessment, not a guarantee of safety.

Run `npm audit` on the deployment date, review remaining advisories, and apply compatible fixes followed by the complete verification suite. Do not expose Next.js development server, Vitest UI, Prisma tooling or the development API directly to the Internet. Use the production reverse proxy and conventional server stack.
